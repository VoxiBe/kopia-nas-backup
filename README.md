# Kopia NAS Backup

[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](https://opensource.org/licenses/MIT)

A simple automated backup pipeline for a Docker-based NAS using [Kopia](https://kopia.io/), with database-aware backups and Telegram notifications.

The goal is to create consistent database dumps before running Kopia snapshots, rather than relying solely on filesystem-level backups of live databases.

## Features

- Creates database backups before each Kopia snapshot
- PostgreSQL dump for Immich
- Safe SQLite backups for Vaultwarden, Wealthfolio, Yamtrack and Jellyfin
- Redis backup for Yamtrack
- Runs all configured Kopia snapshots
- Detects backup failures and stops the pipeline
- Sends a detailed Telegram notification after each backup
- Reports whether each Kopia snapshot was created or unchanged
- Measures total backup duration
- Designed for unattended scheduled execution

## How it works

The backup process is split into two scripts:

### `orchestrator_backup.sh`

This is the main script. It:

1. Loads the Telegram configuration from `bot.env`
2. Runs `dump_databases.sh`
3. Stops if a database backup fails
4. Runs all configured Kopia snapshots
5. Checks the Kopia output for snapshot failures
6. Sends the result through Telegram

### `dump_databases.sh`

Creates application-aware database backups for:

| Application | Database | Backup method |
|---|---|---|
| Immich | PostgreSQL | `pg_dumpall` |
| Vaultwarden | SQLite | SQLite `.backup` |
| Wealthfolio | SQLite | SQLite `.backup` |
| Yamtrack | SQLite + Redis | SQLite `.backup` + Redis `SAVE` |
| Jellyfin | SQLite | SQLite `.backup` |

The resulting database backups are written to a dedicated directory, which can then be included in the Kopia snapshots.

## Requirements

The current scripts assume:

- A Linux-based NAS
- Bash
- Docker
- Kopia running in a Docker container
- `sqlite3` installed on the NAS
- `curl`
- `gzip`
- A Telegram bot for notifications

The default paths use `/volume1/docker/`.

You will need to adapt the paths and Docker container names to match your own environment.

## Configuration

Create a local `bot.env` file based on `bot.env.example`:

```bash
BOT_TOKEN="YOUR_TELEGRAM_BOT_TOKEN"
CHAT_ID="YOUR_TELEGRAM_CHAT_ID"
KOPIA_CONTAINER="kopia-backup"
```

Then protect it:

```bash
chmod 600 bot.env
```

> [!IMPORTANT]
> Never commit `bot.env` to Git. It contains your Telegram bot credentials.
> The included `.gitignore` prevents `.env` files from being tracked.

## Installation

1. Download or clone this repository.
2. Adapt the paths in `dump_databases.sh` to your Docker configuration.
3. Copy `bot.env.example` to `bot.env`.
4. Add your Telegram bot token and chat ID.
5. Make the scripts executable:

```bash
chmod +x orchestrator_backup.sh dump_databases.sh
```

6. Make sure your Kopia container is running and your snapshot sources are already configured.
7. Test the complete pipeline manually:

```bash
./orchestrator_backup.sh
```

Only schedule the script after verifying that the database dumps, Kopia snapshots and Telegram notifications all work correctly.

## Scheduling

The script can be run automatically using cron or your NAS task scheduler.

For example, a cron entry for a backup every night at 03:00 could look like:

```cron
0 3 * * * /path/to/orchestrator_backup.sh
```

Adapt the path and schedule to your environment.

## Restoring backups

A backup is only useful if it can be restored.

Database files generated by `dump_databases.sh` should first be restored from the appropriate Kopia snapshot. The exact database restoration procedure depends on the application and database engine.

Before relying on this setup for important data, test the complete restoration process for your own environment.

## Security

- Keep `bot.env` private.
- Never publish Telegram tokens, passwords or Kopia repository credentials.
- Restrict `bot.env` permissions to the account running the backup.
- Review and adapt all paths before running the scripts.
- Test restores regularly.

## Disclaimer

This project is provided as-is and was created for a specific self-hosted environment.

Review and adapt the scripts before using them on your own system. Always maintain multiple independent backups of important data and test your restoration procedures.
